# 日本語→英語命名 補完プラグイン 設計書

作成日: 2026-11-08 / 状態: **承認待ち**(未承認。承認されるまで本実装に着手しない)
前提: 試作(`codic/spike/`、使い捨て)の実測結果。この設計書は試作のコードを引き継がない。

設計の考え方は、ミノ駆動のスキル(問題定義 / ドメインモデルの完全性 / インターフェースと実装の分離)に沿う。
各スキルの成果物の様式まで満たすことは目的にしていない。判断の順序と、推測と事実を分ける作法を借りている。

## 1. 問題の定義

### 観測(利用者の発言と試作で確かめた事実)
- 利用者は codic で命名していた。直近の例は `@Scheduled(cron = "0 0 7 * * *")` の値に付ける名前。
  「稼働時刻」を codic に入れ、`operationTime` を得て、コードへ貼った。
- 手間は、コピー・貼り付けの往復(4 操作)と、codic を探して開く操作。
- codic は廃止された。
- 試作で確かめた事実(固定ダミー辞書、fixture テストと利用者の実 IDE 確認):
  - 日本語の確定直後に、標準の補完機構だけで候補が自動表示される。
  - 英字入力時の補完は変わらない。
  - コメント・文字列の中では、自動表示は出ず、手動の補完呼び出しでは候補が出る。

### 目的と成功条件
- 目的: エディタから離れずに、日本語から英語の命名を得る。
- 成功: 日本語を確定した直後に、命名候補がポップアップで出て、選ぶと日本語が英語名に置き換わる。
- 拒否条件(これが起きたら失敗): 英字入力時の既存の予測変換を妨げる。
- 命名の質の基準は、次の codic の記載(出典: https://nelog.jp/codic)。
  1. 文章から名前を作る(「従業員数を取得する」から `get_employee_count`)
  2. 「〜か」で終わる句は真偽値の名前にする(`should_` / `is_` / `has_`)
  3. 単語ごとの別候補を出せる(`get` と `fetch` など)
  4. 複数形に対応する(`person` から `people` を含む)
  5. ケース変換(Pascal、camel、snake、SNAKE、ハイフン)
  6. 語順の入れ替えと、複数語の結合
  7. 辞書に無い語を利用者が追加できる

### 制約(利用者が決めたこと)
- 永続で無料。有料 API は使わない。
- IntelliJ IDEA Community Edition 2025.2.6.2 で動く。
- 対象言語は Java のみ(Kotlin は後で別途)。
- 確定後に自動で出す。日本語のときだけ動く。コメント・文字列で出ないに越したことはないが、さほど邪魔ではない。

### 前提・未確認(推測を事実として扱わない)
- 外部サービスの利用は許容された。ただし「永続で無料」と両立しないため、**私の判断**で辞書はオフライン同梱とした(§5)。
- 汎用辞書は JMdict(CC BY-SA 4.0)を採用する。その義務の及ぶ範囲のうち、未確認の点は §7-1b。
- 形態素解析ライブラリの同梱辞書のライセンスは**未確認**(§7-2)。

## 3. 用語(ユビキタス言語)

| 用語 | 意味 |
|---|---|
| 日本語句 | 利用者が確定した日本語の文字列(例: 稼働時刻、従業員数を取得する) |
| 命名種別 | 作る名前の用途。変数、定数、メソッド、クラス、真偽値のいずれか |
| 英単語 | 日本語の語に対応づけた、命名に使う英語の一語(例: employee、get) |
| 英語名 | 英単語の並びと、ケースの規則で決まる一つの識別子(例: `getEmployeeCount`) |
| 命名候補 | 利用者に提示する英語名。別訳を持つ英単語の差し替えで、複数になる |
| 命名規則 | 英語名の綴り方(camel、Pascal、snake、SNAKE、ハイフン) |
| 辞書 | 日本語の語から英単語への対応表。同梱辞書と利用者辞書がある |

「命名種別」と「命名規則」を混ぜない。種別は用途(何を作るか)、規則は綴り方。
種別から規則の既定値は決まる(変数は camel、定数は SNAKE、クラスは Pascal)が、別の概念である。

## 4. ドメインモデルの完全性(欠落の点検)

- **英語名**は不正な状態を作れないようにする。英単語が 0 個の英語名は存在させない。
  Java の識別子として使えない文字列(数字始まり、予約語)は、候補として出す前に除く。
  → これは「英語名」を作るときの検査として、値を作る箇所に集める。呼び出し側に散らさない。
- **辞書の書き手**は 2 つある。同梱辞書(読み取り専用。配布物に含まれる)と、利用者辞書(利用者が追加・編集)。
  同じ語が両方にあるときは、利用者辞書を優先する(私の判断)。
- **辞書の読み手**は、命名エンジンだけ。IDE 連携の層は辞書を直接読まない。
- **失敗**: 辞書に無い語。→ その語だけ日本語のまま残した候補を、最後尾に出す(§7-1)。
  日本語を一語も解けない句(全語が未登録)は、日本語のままになるため候補を出さない(私の判断)。
- **状態**: 命名エンジンは状態を持たない(同じ入力と辞書から同じ候補を返す)。
  辞書だけが状態を持ち、その書き手は上の 2 つ。

## 5. 構成

試作で分かったとおり、IDE 連携は標準の補完機構にそのまま乗る。そのため、IDE 連携の層は薄くできる。
複雑さは命名エンジンにあるので、エンジンを IntelliJ から切り離す。

```
利用者の入力(日本語を確定)
        │
  [IDE 連携]  補完 contributor(薄い)       ← IntelliJ に依存するのはここだけ
        │  「日本語句 と 文脈 を渡して、命名候補を受け取る」
        ▼
  [命名エンジン]  日本語句 → 命名候補       ← 純粋な Java。IntelliJ を知らない
        │
        ├─ 日本語の解析(語に分ける)
        ├─ 辞書の引き当て(同梱 + 利用者)
        └─ 組み立て(真偽値の接頭辞、複数形、命名規則)
```

### 境界(consumer が知ることと知らなくてよいこと)
- consumer は IDE 連携の層。知ること: 「日本語句と命名種別を渡すと、命名候補の列が返る。候補は英語名と、単語ごとの別訳を持つ」。
- 知らなくてよいこと: 形態素解析の製品名、辞書の保存形式、引き当ての順序。
- 失敗の見せ方: 候補が作れないとき、空の列を返す(例外を IDE 層に漏らさない)。
- 命名エンジンの実装は 1 つだけ。**interface を型として量産しない**。
  実際に差し替えが起きる箇所(辞書の読み出し元: 同梱と利用者)だけ、境界を作る。

### モジュール分割
- `engine`(純粋な Java。単体テストのみで検証できる)
- `plugin`(IntelliJ 連携。`engine` に依存)
- 依存は `plugin → engine` の一方向。

### 辞書の方針(私の判断。未確認事項は §7)
- 同梱辞書は 2 層にする。
  1. **自前のプログラミング用語辞書**: 「取得 → get / fetch」「数 → count / number」「か → is / has / should」のような、命名に特化した対応。ライセンスの縛りが無い。
  2. **汎用の日本語英語辞書(JMdict)**: 1 に無い語の補完用。利用者が採用を決定済み(§7-1)。
- 利用者辞書は、設定画面から追加する。保存はファイル 1 つ(形式は実装時に決める)。

## 6. 品質と検証

| 品質 | 検証の方法 |
|---|---|
| 英字入力を妨げない | 試作のテストのケースと期待値を引き継ぐ。本実装のプラグインの有無で、英字の補完結果が一致することを比較する |
| 日本語で自動表示 | 自動ポップアップのテストと、利用者による実 IDE の確認 |
| 命名の質 | codic の記載例(従業員数を取得する、広告を表示するか、有料プランか 等)を固定の期待値にして、`engine` を単体テストする |
| 永続無料 | 外部通信を一切しないこと。ビルド成果物に通信コードが無いことを確認する |
| 対象バージョン | 2025.2.6.2 を対象にビルドとテストを実行する |

命名の質は、codic の記載例と、利用者が実際に命名した例を、固定の入力と期待値として持つ。
期待値は codic の実出力ではなく、記事に書かれている例だけを根拠にする(codic は廃止されていて実出力は取れない)。

| ID | 決定 |

### 7-1b. Q2 の採用で残る未確認事項(実装者が原本で確認する)
- 辞書を定期的に更新する義務が、オフライン同梱のプラグインにどう及ぶか。更新の手順をどう用意するか(例: プラグインの更新で辞書を差し替える)。
- 命名用に加工した辞書データを CC BY-SA 4.0 で公開する場所と方法。プラグインのコードとは別のライセンスになるため、配布物の中でデータとコードを分けて扱う。
- 出典表示の置き場所(設定画面の「About」など)。

### 7-2. 設計者の判断(利用者は読んで違えば直す)

- **命名種別(旧 Q5)**: 自動判定にする。手動選択は「確定直後に自動で出す」という成功条件と衝突するため。
  判定は `plugin` 内の小さな部品(「文脈の読み取り」)に閉じ込め、`engine` には種別だけを渡す。`plugin` 全体が厚くなるのを避ける。
  初版で判定する文脈は、ローカル変数・フィールド(camel)、定数(`static final`、SNAKE)、メソッド名(camel)、クラス名(Pascal)の 4 つ。
  判定できないときは変数(camel)にする。この判定が実機で成り立つかは**未検証**で、実装の最初に確かめる。
- **候補の順序と件数**: 辞書に載せた順を優先順とし、最大 10 件。codic の記事から決まらないため、この値は仮置き。
- **利用者辞書(初版)**: IDE の設定フォルダに 1 ファイル。1 語に複数の訳を持てる。編集は設定画面の一覧表(追加・編集・削除)。プロジェクト単位の辞書は初版に入れない。
- **形態素解析ライブラリ(旧 Q4)**: Kuromoji が第一候補。ライセンスは Apache 2.0(公式ページで確認)。
  ただし、同梱辞書(IPADIC など)の条件は `NOTICE.md` に書かれていて**未確認**。保守が活発かも記載が無く**未確認**。
  実装の最初に、選定の小さな試作(「従業員数を取得する」「広告を表示するか」を語に分けられるか)を置く。分けられなければ別のライブラリを検討する。
- **ビルド**: Gradle と IntelliJ Platform Gradle Plugin(試作で 2.20.0、Gradle 9.8.2 で動作確認済み)。JDK 21。対象は 2025.2.6.2(`sinceBuild` 252、`untilBuild` 252.*)のみ。
- **試作の引き継ぎ**: 引き継ぐのはテストの「ケースと期待値」であり、試作のコードそのものではない。
- **候補が 1 件のとき**の自動挿入は、手動で補完を呼んだときの標準の振る舞いに従う。
- **フィールド宣言名の位置**で標準の候補(`稼働時刻AnInt` など)が混ざる件は、標準の補完を邪魔しない方針により、そのままにする。

出典: https://www.edrdg.org/edrdg/licence.html (要約。法的助言ではない)

- ソフトでは、ドキュメント等で出典を示し、ライセンスの文書を提供またはリンクする義務がある。
- 辞書を改変・変換した結果物(例: 命名用に加工した辞書)は、同一または互換のライセンスでしか配布できない。
- 辞書データを利用する場合は、最新版へ定期的に更新する手順が必要とされる(Web サーバーは月 1 回以上)。
